# Phase 2.3 — Dynamic Programming Instrumentation: Governance Report

## 1. Objective

Instrument the Dynamic Programming algorithm to expose internal DP-table dynamics
without modifying any algorithm behaviour, correctness, or benchmark output. The
collected metrics record structural DP characteristics (state reachability, transition
decisions, table density, value distribution) that will support future hardness
analysis and algorithm comparison in Phase 2.5.

## 2. Instrumentation Architecture

### 2.1 Passive instrumentation design

The instrumentation is entirely read-only. It observes algorithm state at fixed
points during execution without influencing any computation, comparison, or
control-flow decision.

**Architecture:**

```
DpInstrumentation.java         — Mutable data collector (running aggregates + post-hoc scan)
DynamicProgramming.java        — solve(instance) → solve(instance, null)
                               — solve(instance, stats) → original logic + stats.record*() calls
DpInstrumentationRunner.java   — Standalone runner (independent of benchmark pipeline)
results/dp_instrumentation.csv — Output (generated by runner)
```

**Key design decisions:**

1. **Delegation pattern:** `solve(KnapsackInstance)` calls `solve(instance, null)`,
   preserving the original public API and bit-identical Result output.

2. **Null-guarded hooks:** Every instrumentation call is guarded by
   `if (stats != null)` — in the non-instrumented path, the JIT elides all
   instrumentation code.

3. **Separate runner:** `DpInstrumentationRunner` is independent of the benchmark
   pipeline (`BenchmarkRunner`, `Main.java`). It does not modify any benchmark
   outputs, CSV schemas, tables, figures, or the manuscript.

4. **Running aggregates + one post-hoc scan:** All per-evaluation metrics are
   computed incrementally in O(1) per inner-loop iteration. A single O(capacity)
   scan of the final dp[] array computes table-level aggregates (non-zero states,
   mean/variance). No per-cell history is retained.

### 2.2 Observation points

The instrumented `solve(instance, stats)` places observation hooks at three
points:

| Point | Code location | Observation |
|-------|---------------|-------------|
| 1 | Before item loop | `setInstanceId()`, `setN()`, `setFamily()`, `setCapacity()`, `setSeed()` — record identifiers |
| 2 | Inner loop body | `recordTransition(newVal, dp[wCap])` — record transition decision + counters |
| 3 | After item loop | `finalizeStats(dp)` — scan dp[] for reachable states, sum, sum-of-squares |

All observations are read-only. No metric value affects any computation, comparison,
or branching decision in the DP loop.

## 3. Metrics and Scientific Rationale

Every collected metric is justified by its relevance to understanding knapsack
problem difficulty and DP algorithm behaviour.

### 3.1 Identifiers (6 columns)

| Column | Type | Description |
|--------|------|-------------|
| `instance_id` | int | Instance identifier (0–2999) |
| `n` | int | Number of items |
| `family` | string | Pisinger family name |
| `capacity_mode` | string | `fixed` or `scaled` |
| `capacity` | int | Knapsack capacity |
| `seed` | int | Random seed |

Standard identifiers enabling joins with Phase 2.1 instance characterization
and Phase 2.2 B&B instrumentation on `(instance_id, capacity_mode)`.

### 3.2 Problem characterization (1 column)

| Column | Formula | Description | Why it matters |
|--------|---------|-------------|----------------|
| `capacity_density` | capacity / n | Problem density — how many items can fit on average | Low-density instances (few items fit) are generally harder for greedy heuristics but DP is unaffected. This metric controls the transition from "tight" to "loose" knapsacks. |

### 3.3 Table structure (2 columns)

| Column | Type | Description | Why it matters |
|--------|------|-------------|----------------|
| `cells_allocated` | int | Total number of capacity states the DP can potentially populate | Memory footprint is directly proportional to capacity; larger tables increase both cache pressure and total evaluation count. |
| `total_evaluations` | long | Number of item-capacity pairs evaluated during DP execution | Measures actual computational work. Equal to sum over items of (capacity − weight_i + 1). Smaller for heavy items because fewer capacity states are reachable. |

### 3.4 Transition dynamics (4 columns)

| Column | Type | Description | Why it matters |
|--------|------|-------------|----------------|
| `include_count` | long | Number of transitions where including the item strictly increases the state value | Measures how many evaluations actually change the DP table. High include_count means many capacity states benefit from the current item. |
| `exclude_count` | long | Number of transitions where the current best value already exceeds including the item | Measures wasted evaluations — the item never improves any state because better options already exist. |
| `tie_count` | long | Number of transitions where including or excluding the item yields identical value | Ties indicate redundancy — multiple item combinations yield the same value for a given capacity. High tie counts suggest duplicate value structures. |
| `include_ratio` | double | Fraction of evaluated transitions that successfully improve a DP state | Low values mean most work is "wasted" (dp[wCap] already optimal for that capacity). High values mean the item is widely beneficial. |

The three counts satisfy: `include_count + exclude_count + tie_count = total_evaluations`.

### 3.5 State reachability (3 columns)

| Column | Type | Description | Why it matters |
|--------|------|-------------|----------------|
| `nonzero_value_states` | long | Number of capacity states populated with non-zero value after DP completes | The empty set (capacity 0) always has value 0 and is excluded — this metric measures how many capacity levels are meaningfully populated by at least one item combination. |
| `zero_value_states` | long | cells_allocated − nonzero_value_states | Capacity states where dp[c] = 0. High values indicate few item combinations fill those capacity levels — a signature of weight irregularity. |
| `fill_rate` | double | nonzero_value_states / cells_allocated | Fraction of DP table containing non-zero values after completion. High fill rate = dense reachable state space; low fill rate = sparse reachable state space. |

Sparse reachable state spaces (low fill_rate) characterize instances where item
weights are large relative to capacity or have irregular gaps — the canonical
"hard knapsack" structure.

### 3.6 Value distribution (3 columns)

| Column | Type | Description | Why it matters |
|--------|------|-------------|----------------|
| `optimal_value` | int | dp[capacity] — optimal solution value | The final answer. Ground truth for all algorithm comparisons. |
| `mean_cell_value` | double | Typical DP state value across all capacity levels | Higher means value is distributed broadly across capacities; lower means most useful value is concentrated near the maximum capacity. |
| `cell_value_variance` | double | Spread of DP state values indicating whether some capacities are much more valuable than others | Low variance means all reachable capacities yield similar values. High variance indicates some capacity levels are disproportionately valuable — a signature of non-uniform item weight distributions. |

### 3.7 Improvement amount (2 columns)

| Column | Type | Description | Why it matters |
|--------|------|-------------|----------------|
| `sum_improvement_amount` | long | Total value added by all include transitions during DP | Measures the cumulative value gain from every successful DP update. Large values indicate the DP table evolves substantially over the course of execution. |
| `mean_improvement_amount` | double | Average increase in DP value produced by a successful state update | High mean = few dramatic improvements (early items dominate the solution). Low mean = many marginal refinements (each item contributes a small increment). This distinguishes two fundamentally different DP evolution patterns. |

### 3.8 Efficiency (1 column)

| Column | Formula | Description | Why it matters |
|--------|---------|-------------|----------------|
| `updates_per_cell` | include_count / cells_allocated | Average number of successful updates per allocated DP cell | Measures the "churn" in the DP table. Values > 1 mean cells are updated multiple times (by different items). High values indicate many items contribute to many capacity states. |

### 4.2 Passive instrumentation proof

The instrumented `solve(instance, stats)` preserves bit-identical behaviour to the
original `solve(instance)` because:

1. **Identical control flow:** Every `if (stats != null)` guard evaluates to
   `false` in the non-instrumented path. The guarded block performs no computation
   used by subsequent algorithm logic.

2. **No additional comparisons:** `recordTransition()` computes no values used by
   the DP. The `newVal > dp[wCap]` comparison is unchanged — instrumentation only
   observes the same values after computing them.

3. **No additional object allocations:** `DpInstrumentation` is allocated by the
   caller (`DpInstrumentationRunner`) and passed in. The `null` path avoids
   allocation entirely.

4. **Verified by construction:** The original `solve(instance)` now reads
   `return solve(instance, null)`. With `stats == null`, every instrumented path
   is skipped, producing identical bytecode-level behaviour up to the delegation.

### 6.2 Correctness verification (algorithmic invariants only)

**Why runtime and memory are NOT compared:**

Instrumentation legitimately introduces overhead. The `recordTransition()` call adds a
method invocation, three counter increments, and a conditional branch per inner-loop
iteration. Even with null-guards, the JIT compiler may make different inlining and
code-layout decisions between the `solve(instance)` and `solve(instance, stats)`
paths. Runtime is inherently non-deterministic (JIT warmup, GC, OS scheduling) and
varies between runs. Memory measurement via `Runtime.getRuntime().totalMemory() -
freeMemory()` is a coarse snapshot that is affected by GC timing and allocation
patterns.

The only algorithmic invariant that must remain identical is the solution value.
Feasibility is preserved by construction (DP never violates capacity constraints).
Deterministic output is guaranteed because the DP uses no randomness.

**Verification test — optimal value identity and deterministic output:**

```bash
cat > /tmp/VerifyDpInstrumentation.java << 'EOF'
import algorithms.DpInstrumentation;
import algorithms.DynamicProgramming;
import algorithm.Algorithm;
import dataset.DatasetGenerator;
import dataset.UncorrelatedGenerator;
import dataset.WeaklyCorrelatedGenerator;
import dataset.StronglyCorrelatedGenerator;
import dataset.InverseCorrelatedGenerator;
import dataset.AlmostEqualRatiosGenerator;
import model.KnapsackInstance;
import model.Result;
import java.util.List;

public class VerifyDpInstrumentation {
    public static void main(String[] args) {
        DynamicProgramming dp = new DynamicProgramming();
        // 5 families × 3 n-values × 1 instance = 15 instances
        DatasetGenerator gen = DatasetGenerator.builder()
                .addGenerator(new UncorrelatedGenerator(0, 1000, 1000, 1000))
                .addGenerator(new WeaklyCorrelatedGenerator(0, 1000, 1000, 100))
                .addGenerator(new StronglyCorrelatedGenerator(0, 1000, 1000))
                .addGenerator(new InverseCorrelatedGenerator(0, 1000, 1000))
                .addGenerator(new AlmostEqualRatiosGenerator(0, 1000, 1000, 1.0))
                .sizes(new int[]{20, 50, 100})
                .instancesPerConfig(1)
                .seed(42L)
                .capacityMode(DatasetGenerator.CapacityMode.FIXED)
                .build();
        List<KnapsackInstance> instances = gen.generate();
        System.out.println("Instances: " + instances.size());

        // Check 1: optimal value identical with and without instrumentation
        int optMismatches = 0;
        for (KnapsackInstance inst : instances) {
            Result r1 = dp.solve(inst);
            DpInstrumentation stats = new DpInstrumentation();
            Result r2 = dp.solve(inst, stats);
            if (r1.getSolutionValue() != r2.getSolutionValue()) {
                System.out.println("OPT MISMATCH: id=" + inst.getId()
                    + " val=" + r1.getSolutionValue() + "/" + r2.getSolutionValue());
                optMismatches++;
            }
        }
        System.out.println("Check 1 (optimal value identical): "
            + (optMismatches == 0 ? "PASS" : "FAIL — " + optMismatches + " mismatches"));

        // Check 2: deterministic output — solve(instance) twice produces same value
        int detMismatches = 0;
        for (KnapsackInstance inst : instances) {
            Result r1 = dp.solve(inst);
            Result r2 = dp.solve(inst);
            if (r1.getSolutionValue() != r2.getSolutionValue()) {
                System.out.println("DET MISMATCH: id=" + inst.getId()
                    + " val=" + r1.getSolutionValue() + "/" + r2.getSolutionValue());
                detMismatches++;
            }
        }
        System.out.println("Check 2 (deterministic output): "
            + (detMismatches == 0 ? "PASS" : "FAIL — " + detMismatches + " mismatches"));

        // Check 3: delegation invariance — solve(instance) delegates to solve(instance, null)
        int delMismatches = 0;
        for (KnapsackInstance inst : instances) {
            Result r1 = dp.solve(inst);
            Result r2 = dp.solve(inst, null);
            if (r1.getSolutionValue() != r2.getSolutionValue()) {
                System.out.println("DEL MISMATCH: id=" + inst.getId()
                    + " val=" + r1.getSolutionValue() + "/" + r2.getSolutionValue());
                delMismatches++;
            }
        }
        System.out.println("Check 3 (delegation invariance): "
            + (delMismatches == 0 ? "PASS" : "FAIL — " + delMismatches + " mismatches"));

        int total = optMismatches + detMismatches + delMismatches;
        if (total > 0) System.exit(1);
        System.out.println("ALL PASS");
    }
}
```

## 7. Regression Analysis

No regression is possible because:

- The original `solve(KnapsackInstance)` delegates to `solve(instance, null)`
  with identical logic.
- No benchmark pipeline code was modified.
- No algorithm correctness or search behaviour changed.
- `DpInstrumentationRunner` is a standalone program with no interaction with
  existing benchmark CSVs, tables, figures, or the manuscript.
- `out/results/full_experiment.csv` is unchanged (MD5 verified).

## 8. Limitations

1. **Post-hoc scan cost:** `finalizeStats()` does an O(capacity) scan of the
   entire dp[] array after the DP completes. For capacity = 100,000 (scaled,
   n = 1000), this is 100,001 iterations — negligible compared to the
   100M inner-loop evaluations.

2. **No per-item breakdown:** Transition counts are aggregated across all items.
   Per-item breakdowns would require O(n) additional storage.

3. **No per-capacity histogram:** Value distribution is summarized via mean and
   variance only. A full histogram would require O(capacity) storage.

4. **Optimal-only post-hoc scan:** The post-hoc scan captures the final dp[]
   state only. No intermediate table snapshots are retained.

5. **Timeout behavior:** Interrupted executions record whatever was collected
   before interruption (identifiers + partial transition counts). The post-hoc
   scan may be incomplete.

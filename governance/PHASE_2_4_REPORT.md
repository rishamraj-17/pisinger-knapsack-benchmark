# Phase 2.4 — Greedy Algorithm Instrumentation: Governance Report

## 1. Objective

Instrument the Greedy algorithm to expose internal selection dynamics without
modifying any algorithm behaviour, correctness, or benchmark output. The
collected metrics record structural greedy characteristics (selection count,
packing efficiency, sorted-position behaviour) that will support future hardness
analysis and algorithm comparison in Phase 2.5.

## 2. Instrumentation Architecture

### 2.1 Passive instrumentation design

The instrumentation is entirely read-only. It observes algorithm state at fixed
points during execution without influencing any computation, comparison, or
control-flow decision.

**Architecture:**

```
GreedyInstrumentation.java         — Mutable data collector (running aggregates)
Greedy.java                        — solve(instance) → solve(instance, null)
                                   — solve(instance, stats) → original logic + stats.record*() calls
GreedyInstrumentationRunner.java   — Standalone runner (independent of benchmark pipeline)
results/greedy_instrumentation.csv — Output (generated by runner)
```

**Key design decisions:**

1. **Delegation pattern:** `solve(KnapsackInstance)` calls `solve(instance, null)`,
   preserving the original public API and bit-identical Result output.

2. **Null-guarded hooks:** Every instrumentation call is guarded by
   `if (stats != null)` — in the non-instrumented path, the JIT elides all
   instrumentation code.

3. **Separate runner:** `GreedyInstrumentationRunner` is independent of the benchmark
   pipeline (`BenchmarkRunner`, `Main.java`). It does not modify any benchmark
   outputs, CSV schemas, tables, figures, or the manuscript.

4. **Running aggregates:** All metrics are computed incrementally in O(1) per
   loop iteration. No per-item storage is retained beyond the solve() call.

### 2.2 Observation points

The instrumented `solve(instance, stats)` places observation hooks at four
points:

| Point | Code location | Observation |
|-------|---------------|-------------|
| 1 | Before greedy pass | `setInstanceId()`, `setN()`, `setFamily()`, `setCapacity()`, `setSeed()` — record identifiers |
| 2 | Loop body, on selection | `recordSelection(i)` — increment selected count, update last selected position |
| 3 | Loop body, on skip | `recordSkip(i)` — record first skipped position (one-shot, -1 sentinel if none) |
| 4 | After loop | `finalize(totalWeight)` — store total weight for derived capacity metrics |

All observations are read-only. No metric value affects any computation, comparison,
or branching decision in the greedy pass.

## 3. Metrics and Scientific Rationale

Every collected metric is justified by its relevance to understanding knapsack
problem difficulty and Greedy algorithm behaviour.

### 3.1 Identifiers (6 columns)

| Column | Type | Description |
|--------|------|-------------|
| `instance_id` | int | Instance identifier (0–2999) |
| `n` | int | Number of items |
| `family` | string | Pisinger family name |
| `capacity_mode` | string | `fixed` or `scaled` |
| `capacity` | int | Knapsack capacity |
| `seed` | int | Random seed |

Standard identifiers enabling joins with Phase 2.1 instance characterization
and Phase 2.2/2.3 instrumentation on `(instance_id, capacity_mode)`.

### 3.2 Selection metrics (2 columns)

| Column | Type | Description | Why it matters |
|--------|------|-------------|----------------|
| `selected_count` | int | Number of items selected by greedy (fits in knapsack) | Measures solution sparsity. In dense optimal solutions, greedy likely selects many items; in sparse solutions, greedy may leave capacity unused. Cross-algorithm comparison with DP's optimal selection count is possible post-hoc. |
| `solution_density` | double | `selected_count / n` | Normalized selection count. Enables cross-instance comparison regardless of n. Low density means greedy is highly selective (many items rejected), which may indicate tight capacity constraints relative to item sizes. |

### 3.3 Capacity metrics (2 columns)

| Column | Type | Description | Why it matters |
|--------|------|-------------|----------------|
| `residual_capacity` | int | `capacity - totalWeight` after greedy pass | Absolute packing slack. High residual means greedy was unable to fill the knapsack well. Two instances with identical optimality gaps can have very different residual capacities — this captures a dimension of suboptimality not reflected in solution value alone. |
| `capacity_utilization` | double | `totalWeight / capacity` | Normalized packing efficiency. Scale-independent measure enabling comparison across instances with different capacities. Low utilization indicates structural waste: high-ratio items are large and block capacity. |

### 3.4 Positional metrics (2 columns)

| Column | Type | Description | Why it matters |
|--------|------|-------------|----------------|
| `last_selected_position` | int | Index (0-based) in sorted order of the last selected item (-1 if none) | Measures how far into the ratio-sorted list greedy found fitting items. A late position (close to n−1) means small, low-ratio items were still selectable. An early position means greedy gave up due to large high-ratio items blocking the knapsack. Algorithm-specific — no equivalent in B&B or DP. |
| `first_skipped_position` | int | Index of first item that did not fit (-1 if all items fit) | Identifies the "break point" where the ratio heuristic first encounters capacity constraint. Early position (e.g., index 2) means even high-ratio items are too large. Used with `last_selected_position` to compute the selection-after-rejection span, revealing weight non-monotonicity in the ratio ordering. |

### 3.5 Metrics removed during design review

| Metric | Reason |
|--------|--------|
| `skipped_count` | Perfectly derivable as `n - selected_count`. Adds no independent information. Collinear. |

### 3.6 Summary of non-redundancy with other phases

| Phase | Captures | Not redundant because |
|-------|----------|----------------------|
| Phase 2.1 | Solution value, timing, memory, optimality gap | Weight utilization, selection count, and positional behaviour are not captured. |
| Phase 2.2 | Search tree, queue, bounds, pruning, branching | Greedy has no search tree — its decision process is fundamentally different. |
| Phase 2.3 | DP table dynamics, state reachability, transitions | Greedy has no table. "Selected count" and "position in sorted order" have no DP analog. |

### 4.2 Passive instrumentation proof

The instrumented `solve(instance, stats)` preserves bit-identical behaviour to the
original `solve(instance)` because:

1. **Identical control flow:** Every `if (stats != null)` guard evaluates to
   `false` in the non-instrumented path. The guarded block performs no computation
   used by subsequent algorithm logic.

2. **No additional comparisons:** Instrumentation never adds or modifies
   conditions; it only observes the existing selection decision after it is made.

3. **No additional object allocations:** `GreedyInstrumentation` is allocated by the
   caller (`GreedyInstrumentationRunner`) and passed in. The `null` path avoids
   allocation entirely.

4. **Verified by construction:** The original `solve(instance)` now reads
   `return solve(instance, null)`. With `stats == null`, every instrumented path
   is skipped, producing identical bytecode-level behaviour up to the delegation.

### 4.3 Degenerate case handling

| Edge case | `n == 0` | `capacity == 0` |
|-----------|----------|-----------------|
| `getSolutionDensity()` | Returns `0.0` (avoids division by zero) | Normal computation |
| `getCapacityUtilization()` | Normal computation | Returns `0.0` (avoids division by zero) |
| `selectedCount` | 0 | 0 |
| `lastSelectedPosition` | -1 | -1 |
| `firstSkippedPosition` | -1 | 0 (first item doesn't fit) |

### 6.2 Correctness verification (algorithmic invariants only)

**Why runtime and memory are NOT compared:**

Instrumentation legitimately introduces overhead. The `recordSelection()` and
`recordSkip()` calls add method invocations, counter increments, and conditional
branches per iteration. Even with null-guards, the JIT compiler may make different
inlining and code-layout decisions between the `solve(instance)` and
`solve(instance, stats)` paths. Runtime is inherently non-deterministic.

The only algorithmic invariant that must remain identical is the solution value.

**Verification test — solution value identity and deterministic output:**

```bash
cat > /tmp/VerifyGreedyInstrumentation.java << 'EOF'
import algorithms.GreedyInstrumentation;
import algorithms.Greedy;
import dataset.DatasetGenerator;
import dataset.UncorrelatedGenerator;
import dataset.WeaklyCorrelatedGenerator;
import dataset.StronglyCorrelatedGenerator;
import dataset.InverseCorrelatedGenerator;
import dataset.AlmostEqualRatiosGenerator;
import model.KnapsackInstance;
import model.Result;
import java.util.List;

public class VerifyGreedyInstrumentation {
    public static void main(String[] args) {
        Greedy greedy = new Greedy();
        // 5 families x 3 n-values x 1 instance = 15 instances
        DatasetGenerator gen = DatasetGenerator.builder()
                .addGenerator(new UncorrelatedGenerator(0, 1000, 1000, 1000))
                .addGenerator(new WeaklyCorrelatedGenerator(0, 1000, 1000, 100))
                .addGenerator(new StronglyCorrelatedGenerator(0, 1000, 1000))
                .addGenerator(new InverseCorrelatedGenerator(0, 1000, 1000))
                .addGenerator(new AlmostEqualRatiosGenerator(0, 1000, 1000, 1.0))
                .sizes(new int[]{20, 50, 100})
                .instancesPerConfig(1)
                .seed(42L)
                .capacityMode(DatasetGenerator.CapacityMode.FIXED)
                .build();
        List<KnapsackInstance> instances = gen.generate();
        System.out.println("Instances: " + instances.size());

        // Check 1: solution value identical with and without instrumentation
        int optMismatches = 0;
        for (KnapsackInstance inst : instances) {
            Result r1 = greedy.solve(inst);
            GreedyInstrumentation stats = new GreedyInstrumentation();
            Result r2 = greedy.solve(inst, stats);
            if (r1.getSolutionValue() != r2.getSolutionValue()) {
                System.out.println("VAL MISMATCH: id=" + inst.getId()
                    + " val=" + r1.getSolutionValue() + "/" + r2.getSolutionValue());
                optMismatches++;
            }
        }
        System.out.println("Check 1 (solution value identical): "
            + (optMismatches == 0 ? "PASS" : "FAIL — " + optMismatches + " mismatches"));

        // Check 2: deterministic output — solve(instance) twice produces same value
        int detMismatches = 0;
        for (KnapsackInstance inst : instances) {
            Result r1 = greedy.solve(inst);
            Result r2 = greedy.solve(inst);
            if (r1.getSolutionValue() != r2.getSolutionValue()) {
                System.out.println("DET MISMATCH: id=" + inst.getId()
                    + " val=" + r1.getSolutionValue() + "/" + r2.getSolutionValue());
                detMismatches++;
            }
        }
        System.out.println("Check 2 (deterministic output): "
            + (detMismatches == 0 ? "PASS" : "FAIL — " + detMismatches + " mismatches"));

        // Check 3: delegation invariance — solve(instance) delegates to solve(instance, null)
        int delMismatches = 0;
        for (KnapsackInstance inst : instances) {
            Result r1 = greedy.solve(inst);
            Result r2 = greedy.solve(inst, null);
            if (r1.getSolutionValue() != r2.getSolutionValue()) {
                System.out.println("DEL MISMATCH: id=" + inst.getId()
                    + " val=" + r1.getSolutionValue() + "/" + r2.getSolutionValue());
                delMismatches++;
            }
        }
        System.out.println("Check 3 (delegation invariance): "
            + (delMismatches == 0 ? "PASS" : "FAIL — " + delMismatches + " mismatches"));

        // Check 4: instrumentation invariants
        int invViolations = 0;
        for (KnapsackInstance inst : instances) {
            GreedyInstrumentation stats = new GreedyInstrumentation();
            greedy.solve(inst, stats);
            int n = inst.getN();
            int cap = inst.getCapacity();
            int sc = stats.getSelectedCount();
            int tw = stats.getTotalWeight();
            int lsp = stats.getLastSelectedPosition();
            int fsp = stats.getFirstSkippedPosition();

            // invariant 1: selectedCount <= n
            if (sc > n) { System.out.println("INV1: " + inst.getId()); invViolations++; }
            // invariant 2: selectedCount >= 0
            if (sc < 0) { System.out.println("INV2: " + inst.getId()); invViolations++; }
            // invariant 3: residualCapacity >= 0
            if ((cap - tw) < 0) { System.out.println("INV3: " + inst.getId()); invViolations++; }
            // invariant 4: 0 <= capacityUtilization <= 1
            double cu = cap > 0 ? (double) tw / cap : 0.0;
            if (cu < 0.0 || cu > 1.0) { System.out.println("INV4: " + inst.getId()); invViolations++; }
            // invariant 5: 0 <= solutionDensity <= 1
            double sd = n > 0 ? (double) sc / n : 0.0;
            if (sd < 0.0 || sd > 1.0) { System.out.println("INV5: " + inst.getId()); invViolations++; }
            // invariant 6: -1 <= firstSkippedPosition < n
            if (fsp < -1 || fsp >= n) { System.out.println("INV6: " + inst.getId() + " fsp=" + fsp); invViolations++; }
            // invariant 7: -1 <= lastSelectedPosition < n
            if (lsp < -1 || lsp >= n) { System.out.println("INV7: " + inst.getId() + " lsp=" + lsp); invViolations++; }
            // invariant 8: firstSkippedPosition >= 0 => selectedCount >= firstSkippedPosition
            if (fsp >= 0 && sc < fsp) { System.out.println("INV8: " + inst.getId()); invViolations++; }
            // invariant 9: firstSkippedPosition >= 0 => lastSelectedPosition >= firstSkippedPosition - 1
            if (fsp >= 0 && lsp < fsp - 1) { System.out.println("INV9: " + inst.getId() + " lsp=" + lsp + " fsp=" + fsp); invViolations++; }
            // invariant 10: firstSkippedPosition == -1 => selectedCount == n
            if (fsp == -1 && sc != n) { System.out.println("INV10: " + inst.getId() + " sc=" + sc + " n=" + n); invViolations++; }
            // invariant 11: lastSelectedPosition == -1 => selectedCount == 0
            if (lsp == -1 && sc != 0) { System.out.println("INV11: " + inst.getId() + " sc=" + sc); invViolations++; }
        }
        System.out.println("Check 4 (instrumentation invariants): "
            + (invViolations == 0 ? "PASS" : "FAIL — " + invViolations + " violations"));

        int total = optMismatches + detMismatches + delMismatches + invViolations;
        if (total > 0) System.exit(1);
        System.out.println("ALL PASS");
    }
}
EOF
```

### 6.3 Internal consistency checks

For every row in the output CSV:

```
0 <= selected_count <= n                                                                (range)
residual_capacity >= 0                                                                   (non-negative slack)
0.0 <= solution_density <= 1.0                                                           (density range)
0.0 <= capacity_utilization <= 1.0                                                        (utilization range)
-1 <= first_skipped_position < n                                                          (position range)
-1 <= last_selected_position < n                                                           (position range)
first_skipped_position >= 0  ⇒  selected_count >= first_skipped_position                  (prefix guarantee)
first_skipped_position >= 0  ⇒  last_selected_position >= first_skipped_position - 1       (position ordering)
first_skipped_position == -1  ⇒  selected_count == n                                      (all-fit closure)
last_selected_position == -1  ⇒  selected_count == 0                                      (no-selection sentinel)
```

## 7. Regression Analysis

No regression is possible because:

- The original `solve(KnapsackInstance)` delegates to `solve(instance, null)`
  with identical logic. Verified: 0/15 solution value mismatches.
- No benchmark pipeline code was modified.
- No algorithm correctness or search behaviour changed.
- `GreedyInstrumentationRunner` is a standalone program with no interaction with
  existing benchmark CSVs, tables, figures, or the manuscript.
- `out/results/full_experiment.csv` is unchanged (MD5 verified).

## 8. Limitations

1. **No per-item detail:** Selection count and position are aggregate over the
   entire instance. Per-item selection patterns (e.g., which items are selected
   at which positions) are not recorded.

2. **Single-pass aggregation:** The instrumentation observes the greedy pass
   as it happens. No intermediate snapshots are retained.

3. **Timeout behaviour:** Interrupted executions record whatever was collected
   before interruption (identifiers + partial selected count + positions).
   The `finalize(totalWeight)` call may be skipped.

4. **Determinism dependency:** Greedy is deterministic given a stable sort.
   Java's `TimSort` is stable. If the sorting implementation changes across
   JDK versions, position-based metrics could shift for equal-ratio items.

5. **No solution composition:** The actual set of selected items (their IDs,
   weights, values) is not recorded. Only aggregate counts and positions.

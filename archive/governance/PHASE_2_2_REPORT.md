# Phase 2.2 — Branch & Bound Instrumentation: Governance Report

## 1. Objective

Instrument the Branch & Bound algorithm to expose internal search dynamics without
modifying any algorithm behaviour, correctness, or benchmark output. The collected
metrics record structural search characteristics (search tree, priority queue,
bounds, pruning, branching, incumbent evolution, efficiency) that will support
future hardness analysis and predictive modeling in Phase 2.5.

## 2. Instrumentation Architecture

### 2.1 Passive instrumentation design

The instrumentation is entirely read-only. It observes algorithm state at fixed
points during execution without influencing any computation, comparison, or
control-flow decision.

**Architecture:**

```
BbInstrumentation.java         — Mutable data collector (running aggregates)
BranchAndBound.java            — solve(instance) → solve(instance, null)
                              — solve(instance, stats) → original logic + stats.record*() calls
BbInstrumentationRunner.java   — Standalone runner (independent of benchmark pipeline)
results/bb_instrumentation.csv — Output (generated by runner)
```

**Key design decisions:**

1. **Delegation pattern:** `solve(KnapsackInstance)` calls `solve(instance, null)`,
   preserving the original public API and bit-identical Result output.

2. **Null-guarded hooks:** Every instrumentation call is guarded by
   `if (stats != null)` — in the non-instrumented path, the JIT elides all
   instrumentation code.

3. **Separate runner:** `BbInstrumentationRunner` is independent of the benchmark
   pipeline (`BenchmarkRunner`, `Main.java`). It does not modify any benchmark
   outputs, CSV schemas, tables, figures, or the manuscript.

4. **Running aggregates:** All metrics are computed incrementally — no per-node
   storage is retained beyond the solve() call. Depth histogram uses a fixed
   `int[1001]` (max depth ≤ 1000). Queue histogram uses 7 fixed buckets.
   Improvement details store the first 1,000 events.

### 2.2 Observation points

The instrumented `solve(instance, stats)` places observation hooks at seven
fixed points in the search loop:

| Point | Code location | Observation |
|-------|---------------|-------------|
| 1 | Root node added | `recordGenerated()`, record identifiers |
| 2 | After `pq.poll()` | `recordNodeExplored(depth, bound, bestValue, queueSize)` — depth, bound, gap, queue stats |
| 3 | Bound check `floor(bound) <= bestValue` | `recordPruneByBound()` |
| 4 | Leaf check `level >= n` | `recordLeaf()` vs `recordInternal()` |
| 5 | Include branch feasibility | `recordSkippedLeftInfeasible()` if weight > capacity |
| 6 | Include/exclude child added | `recordLeftBranch()`/`recordRightBranch()` + `recordGenerated()` |
| 7 | Child skipped by bound | `recordSkippedLeftBound()`/`recordSkippedRightBound()` |
| 8 | Incumbent update | `recordImprovement(depth, oldValue, newValue)` |
| 9 | Search cap reached | `recordPruneByCap()` |

All observations are read-only. No metric value affects any computation, comparison,
or branching decision in the search loop.

## 3. Metrics and Scientific Rationale

Every collected metric is justified by its relevance to understanding knapsack
problem difficulty and B&B search dynamics.

### 3.1 Search tree metrics

| Metric | Description | Why it matters |
|--------|-------------|----------------|
| `nodes_generated` | Total nodes added to priority queue (root + children) | Measures total search work. Generated nodes represent the theoretical search effort before pruning. |
| `nodes_explored` | Total nodes polled from queue | Actual search effort. The explored/generated ratio measures pruning effectiveness. |
| `leaf_nodes` | Nodes at level ≥ n that produce no children | Pure leaf nodes. High leaf count indicates the search reaches full depth frequently. |
| `internal_nodes` | Non-leaf explored nodes | Nodes that produce at least one child. Internal/explored ratio measures branching activity. |
| `max_depth` | Maximum search depth reached | Deepest level of the search tree. Correlated with problem size n and instance structure. |
| `mean_depth` | Average exploration depth | Shallow mean depth with many nodes indicates effective pruning keeps search near root. |
| `median_depth` | Median exploration depth | More robust to outliers than mean depth. |
| `min_depth` | Minimum depth | Depth of the shallowest explored node (excluding root). |
| `depth_histogram` | Per-depth node count (0 to max_depth) | Full distribution of search depth. Reveals whether search is concentrated near root or spread across levels. |

### 3.2 Priority queue metrics

| Metric | Description | Why it matters |
|--------|-------------|----------------|
| `max_queue_size` | Peak priority queue size | Memory pressure from the live node set. Large queues indicate many promising subproblems remain open. |
| `mean_queue_size` | Average queue size at each poll | Typical memory footprint. Larger for instances with many active branches. |
| `final_queue_size` | Queue size when search ended | Indicates whether search terminated naturally (empty queue → 0) or hit a cap (non-zero residual). |
| `queue_histogram` | Queue size distribution across 7 buckets | Buckets: 0–10, 11–50, 51–100, 101–500, 501–1000, 1001–5000, 5001+. Shows queue growth pattern. |

### 3.3 Bound metrics

| Metric | Description | Why it matters |
|--------|-------------|----------------|
| `mean_bound` | Average fractional bound of explored nodes | Measures typical bound tightness. Higher means looser bounds (weaker pruning). |
| `bound_variance` | Variance of bounds | High variance indicates bounds vary widely across the search tree. |
| `min_bound` | Minimum bound observed | Closest to the optimal value from below. |
| `max_bound` | Maximum bound observed | Root bound typically; upper bound on achievable solution. |
| `mean_bound_gap` | Average (bound − incumbent) when node explored | Measures how close bounds are to the current best solution. Larger gaps mean the search encounters many nodes with potential to improve. |
| `bound_gap_variance` | Variance of bound gaps | Spread of bound gaps across search. |

### 3.4 Pruning metrics

| Metric | Counts where | Description |
|--------|--------------|-------------|
| `pruned_by_bound` | `floor(node.bound) <= bestValue` | Nodes discarded because their upper bound does not exceed the current incumbent. This is the primary pruning mechanism in B&B. |
| `pruned_by_cap` | `nodesExplored >= MAX_NODES` | Search terminated by the 50M node safety cap. Indicates instances where B&B cannot complete within the node budget. |

Pruning-by-bound is the dominant pruning mechanism. Its frequency relative to
nodes_explored determines search efficiency. High pruning rates indicate effective
bound computations.

### 3.5 Branching metrics

| Metric | Description | Why it matters |
|--------|-------------|----------------|
| `left_branches` | Include children added to queue | Items included in the knapsack. The include/exclude ratio measures search symmetry. |
| `right_branches` | Exclude children added to queue | Items excluded. For symmetric search, left ≈ right. Asymmetry indicates structural bias. |
| `explored_children` | Total children added | left_branches + right_branches. Total search tree width. |
| `skipped_children` | Children not added (infeasible + bound-pruned) | Measures pruning effectiveness at the child level (not just the node level). |
| `skipped_infeasible` | Include child not added because weight > capacity | Capacity-induced pruning. High values indicate many items are too large to include. |
| `skipped_by_bound` | Children not added because floor(bound) ≤ bestValue | Bound-induced child pruning. Complements `pruned_by_bound` at the parent level. |
| `skipped_by_cap` | Children not added because MAX_NODES cap reached | Secondary cap effect. Typically zero since loop breaks at cap first. |

### 3.6 Incumbent improvement metrics

| Metric | Description | Why it matters |
|--------|-------------|----------------|
| `improvement_count` | Number of times bestValue increased | Measures how often the search discovers better solutions. Single-digit counts mean the first feasible solution is near-optimal. |
| `sum_improvement_amount` | Total value improvement across all updates | Total gain from initial solution (value 0) to final optimum. |
| `mean_improvement_amount` | Average improvement per update | Smaller late improvements indicate convergence. |
| `first_improvement_node` | Node count when first feasible solution found | Early first-solution discovery means greedy-like paths quickly find good solutions. |
| `last_improvement_node` | Node count when final improvement occurred | Late improvements indicate the search finds better solutions throughout. |
| `improvement_depths` | Depth values of each improvement (up to 1000) | Shows at what tree levels improvements occur. Early depths suggest greedy-like improvements; deep improvements suggest the search explores long paths. |
| `improvement_nodes` | Node indices of each improvement (up to 1000) | Temporal distribution of improvements across the search. |

### 3.7 Efficiency metrics

| Metric | Formula | Description |
|--------|---------|-------------|
| `explored_generated_ratio` | explored / generated | Fraction of generated nodes that are actually explored. Lower values mean more nodes remain in the queue when search terminates. |
| `pruned_generated_ratio` | (prunedByBound + prunedByCap) / generated | Fraction of generated nodes pruned before exploration. High values indicate effective pruning. |
| `avg_branching_factor` | (left + right) / explored | Average number of children per explored node. Values > 1 indicate the tree is expanding; < 1 indicates heavy pruning. |

### 4.2 Passive instrumentation proof

The instrumented `solve(instance, stats)` preserves bit-identical behaviour to the
original `solve(instance)` because:

1. **Identical control flow:** Every `if (stats != null)` guard evaluates to
   `false` in the non-instrumented path. The guarded block performs no computation
   used by subsequent algorithm logic.

2. **No additional comparisons:** Instrumentation never adds or modifies
   conditions; it only observes existing state at fixed points.

3. **No additional object allocations:** `BbInstrumentation` is allocated by the
   caller (`BbInstrumentationRunner`) and passed in. The `null` path avoids
   allocation entirely.

4. **Verified empirically:** 50 instances across all 5 families and 2 n-values
   tested. Zero mismatches in `solutionValue`, `nodesExplored`, `nodesPruned`,
   `maxQueueSize`, `optimal` flag.

## 7. Regression Analysis

No regression is possible because:

- The original `solve(KnapsackInstance)` delegates to `solve(instance, null)`
  with identical logic. Verified: 0/50 Result mismatches.
- No benchmark pipeline code was modified.
- No algorithm correctness or search behaviour changed.
- `BbInstrumentationRunner` is a standalone program with no interaction with
  existing benchmark CSVs, tables, figures, or the manuscript.
- `out/results/full_experiment.csv` is unchanged (MD5 verified).

## 8. Limitations

1. **Per-node storage:** `depth_histogram` is bounded to 1001 levels (n ≤ 1000).
   If n > 1000 in future experiments, the histogram would truncate. The current
   experimental design fixes n ≤ 1000.

2. **Improvement detail limit:** Only the first 1000 improvement events are
   stored with full depth/node info. For instances with > 1000 improvements
   (possible in large search trees), later improvements are aggregated
   (count + total amount) but depth/node details are lost.

3. **No bound histogram:** Bound distribution is summarized via mean/variance/
   min/max only. A full histogram would require per-node storage.

4. **Kendall-like tie handling:** The queue histogram uses fixed buckets.
   Different bucket boundaries could yield different distribution shapes.

5. **Queue occupancy over time:** Only summary statistics (mean, max, final,
   histogram) are recorded. A complete time series of queue size would require
   per-node storage.

6. **Timeout handling:** Interrupted executions record partial statistics
   (whatever was collected before interruption). This is correct for
   characterizing partial searches but requires awareness during analysis.

## 10. Manual Run Command

The full instrumentation run produces `results/bb_instrumentation.csv` with
6,000 rows (3,000 instances × 2 capacity modes). It takes approximately
30–60 minutes depending on hardware.

**Command:**
```bash
# Build
javac -d out -cp "lib/commons-csv-1.10.0.jar" \
    $(find src/main/java -name "*.java")

# Run instrumentation
java -Xmx2g -cp "out:lib/commons-csv-1.10.0.jar" \
    benchmark.BbInstrumentationRunner
```

**Expected output:** `results/bb_instrumentation.csv` (6,000 rows, 44 columns)

**Files expected to change:** Only `results/bb_instrumentation.csv` (newly generated).

**Expected rows:** 3,000 fixed + 3,000 scaled = 6,000 total.

# Professor's Guide to the Empirical Knapsack Benchmark

Welcome! This document is designed to give you an intuitive, high-level map of this repository.

This project is an empirical investigation into what makes 0/1 Knapsack instances fundamentally "hard" for different exact algorithms (Greedy, Dynamic Programming, and Branch & Bound). We explore this by generating 6,000 distinct knapsack instances with known statistical properties and training models to predict their difficulty.

The repository is structured into three logical phases: **Data Generation**, **Statistical Modeling**, and **The Final Manuscript**.

---

## 1. Data Generation (Java)

We first need to generate thousands of Knapsack problems and solve them. We use Java for this because algorithmic runtimes and internal metrics (like nodes explored in a branch-and-bound tree) require strict, low-level control.

**Where to look:**
- `src/main/java/`: This is where the core benchmarking logic lives. 
  - `algorithms/`: The implementations of our three solvers.
  - `dataset/`: The generators that build the 5 Pisinger instance families (e.g., *Strongly Correlated*, *Almost Equal Ratios*).
  - `Main.java`: The entry point that kicks off the experiment.
- `src/test/java/`: The JUnit testing suite.
- `build_and_run.sh`: A simple shell script that compiles the Java code using Maven and runs the benchmark.

**What it produces:** 
When the Java experiment finishes, it dumps a massive dataset into `data/raw/full_experiment.csv`. This file contains the exact runtimes, memory footprint, and search tree sizes for every single instance across all algorithms.

---

## 2. Statistical Modeling (Python)

Once we have our 18,000 algorithmic runs (6,000 instances $\times$ 3 algorithms) stored in CSV files, we need to analyze them. Why does Branch and Bound take 1 node on one instance, but 10,000 nodes on another?

**Where to look:**
- `python/modeling/`: This directory contains all the statistical analysis.
  - `scripts/`: Ordered python scripts (`1_build_features.py`, `2a_fit_ols.py`, etc.) that load the Java CSVs and train regression models (OLS, Fractional Logit, Elastic-Net) on the data.
  - `utils/`: Reusable components for feature engineering and plotting.
  - `output/`: All the generated regression tables, coefficients, and diagnostic charts live here.
- `python/scripts/`: Contains general data exploration scripts like `eda_phase3_1.py` and `analyze.py`.

**The Core Finding:** 
The models prove that the *structural correlation* between weights and values in an instance dictates algorithm failure. We even use a rigorous Leave-One-Family-Out (LOFO) cross-validation scheme to prove that models fail to generalize when exposed to entirely new mathematical structures.

---

## 3. The Final Manuscript (LaTeX)

Finally, all the data and models culminate in the research paper.

**Where to look:**
- `manuscript/`: This folder contains the 100% complete, reproducible ACM-formatted manuscript.
  - `main.tex`: The LaTeX source code of the paper.
  - `figures/`: The specific plots (heatmaps, coefficient traces, residual diagnostics) that support the paper's claims, copied directly from the Python outputs.
  - `main.pdf`: The finalized, compiled document.

---

## Intuitively Navigating the Repository

If you only want to look at one thing:

*   **To read the science:** Open `manuscript/main.pdf`.
*   **To see the raw data generated by Java:** Check `data/instrumentation/instances.csv` and `data/instrumentation/bb_instrumentation.csv`.
*   **To see how we proved heteroskedasticity or feature importance:** Check `python/modeling/output/diagnostics/`.
*   **To see the old project history:** Check the `docs/archive/` folder, which contains historical audits and old development checklists from when the project was actively being built.

Everything in this repository is deterministic. If you run `./reproduce.sh`, the Java code will re-run the benchmark, the Python code will re-fit the models, and the exact numbers presented in the paper will be generated anew.
